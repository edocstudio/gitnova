# ADR 0028 — Submodule changes in the existing Working changes inspector

The submodule flow needs clearer scope, status and action sequencing. A gitlink difference and uncommitted files inside the child are distinct changes. Keep the existing file row, graph/diff dock and submodule inspector; add a submodule icon/type, explicit parent HEAD/index/child checkout values, a direct Open submodule action and a scoped Stage/Unstage pointer review. The generic file Stage action cannot describe this scope safely because child files do not belong to the parent index. Reuse the existing contextual menu and submodule review area rather than a new panel/dialog.

Staging updates only the parent index's existing mode-160000 entry to the reviewed child HEAD; unstaging restores the parent HEAD's existing gitlink. Dirty child files, child index, child refs and child checkout remain untouched. Use a fresh preview, parent operation/index locks, an alternate index, a durable original-index backup and an atomic parent index replacement. Do not use recursive `git add`, checkout, hooks or custom submodule update commands for pointer staging. Reject stale identity/HEAD/index, conflicts and pending parent operations. This slice covers initialized direct submodule pointer updates; add/remove and nested ownership must use their own workflows.

Parent commit review can include reviewed mode-160000 modifications, while additions, removals, type changes and conflicts retain their existing blockers. The full staged diff remains required. Parent commit includes only its staged pointer, never uncommitted child files. Actual push still validates submodule commit availability; pointer staging does not publish child commits.

Restore recorded remains a separate reviewed child-checkout operation with existing dirty/unpushed-work protections. Opening the child is the next step for editing, committing or discarding files inside it. No child changes are implicitly stashed, discarded, committed or moved.
