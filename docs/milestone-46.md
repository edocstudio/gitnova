# M46 — Global company / host CI accounts

User correction: CI setup is global, not repository-specific. One Settings Connections section lists company/host profiles. Each profile contains GitLab or GitHub HTTPS origin and an optional Jenkins controller/account. No repository, branch, commit or Jenkins job is required to add/verify accounts. General language remains global. The original gear is replaced with an original symmetric eight-tooth vector gear and centered circular bore.

These account controls belong in the existing Settings dialog because account identity spans workspaces/repositories; graph context cannot express global account ownership. Reuse the existing Keychain services and native secure prompts, without new screens/panels/navigation. No token enters WebView state or localStorage. Profiles contain bounded nonsecret metadata only (maximum 20). Existing explicit GitLab host preferences migrate to deduplicated global profiles; matching legacy Jenkins controller/username can be retained. Original per-repo/job preferences are not deleted. Unknown hosts are never guessed or promoted. One saved Git hosting account per provider/origin is supported; separate GitHub organizations on github.com do not imply separate account scopes.

Host identity is canonical HTTPS origin plus web base path. Remote matching is native and read-only, using actual fetch URLs, not push URLs. Exact host match; HTTPS ports and base-path segment boundaries must match. SSH hosts match the configured HTTPS host, with SSH transport ports independent. Unmapped SSH aliases require a suitable explicit host configuration; they are never guessed. Prefer a matching origin remote; ambiguous fallback remotes and identical conflicting host scopes are refused. Resolve/revalidate real repository identity and SHA before any CI credential use. Recheck the fetch host on each graph summary read, preventing a changed remote from reading the wrong company's project. No cache is shared across provider/origin/project/account/SHA scopes.

GitLab graphs use the server's commit status. GitHub graphs combine the combined commit-status endpoint with latest check runs, so Actions/checks and Jenkins-reported statuses are represented. Empty results differ from pending; unknown conclusions, inaccessible checks, revision mismatch or incomplete coverage cannot silently become green. At most 100 check runs, two bounded HTTP reads per Github summary; no logs/artifacts. Existing memory caps, serialized provider scheduler, active/terminal cache TTL and hidden-window pause remain in effect. Every result remains an exact SHA match.

Jenkins connection verifies whoAmI for controller plus username with no invented job/revision, preserving old Keychain identity. It is a global account connection, not job discovery: a Jenkins controller alone cannot establish which job/SCM revision built an arbitrary repository. The graph shows Jenkins outcomes reported to GitLab/GitHub. Automatic controller-wide job discovery is not included; UI states this explicitly. Legacy explicit job configurations are retained, not silently remapped or deleted. Native Jenkins build adapter remains covered by transport tests.

Removing a profile stops automatic host matching but retains Keychain entries. Explicit Disconnect separately confirms account removal and its all-repository / PR/MR impact. Editing or removing one host never removes another company's metadata or credential.

Sources: [GitLab commit status](https://docs.gitlab.com/api/commits/#retrieve-a-commit), [GitHub statuses](https://docs.github.com/en/rest/commits/statuses#get-the-combined-status-for-a-specific-reference), [GitHub checks](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference), [Jenkins remote API](https://www.jenkins.io/doc/book/using/remote-access-api/).
